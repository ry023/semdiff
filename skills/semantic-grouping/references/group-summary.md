# Group summary の作成規則

Group summary は、人間がその変更の仕様、実現方法、影響、説明の確かさを理解するための文書です。既存の `Group.summary` に Markdown 全文を保存します。Step は具体的な実装を理解する順序を示し、Fragment は個々の変更を説明します。同じ文章を各階層に複製しません。

## 固定構造

すべての Group で、次の見出しをこの階層・順序で出力します。「検証・根拠」の親見出しと子見出しも両方残します。Group のタイトルは Viewer が表示するため、summary 内に重ねて書きません。

```markdown
### 1. 説明
#### 変更概要
#### 振る舞い
#### 実装・構造
#### 設計判断
### 2. 影響分析
#### 後方互換性
#### セキュリティ
#### データ
#### パフォーマンス
#### 信頼性
#### 運用・リリース
### 3. 検証・根拠
#### 検証・根拠
```

本文は各子見出しの下に書きます。見出し間、段落間には空行を入れ、段落・箇条書き・表を内容に応じて使います。構造だけを固定し、字数、段落数、箇条書きの数は揃えません。小さな変更なら各子セクションは一行でも構いません。説明する情報がなければ、その理由や未確認の範囲を短く書き、一般論で埋めません。

言語は Skill 本体の規則に従います。英語では、同じ階層・順序で次の見出しを使います。

```markdown
### 1. Explanation
#### Change overview
#### Behavior
#### Implementation and structure
#### Design decisions
### 2. Impact analysis
#### Backward compatibility
#### Security
#### Data
#### Performance
#### Reliability
#### Operations and release
### 3. Verification and evidence
#### Verification and evidence
```

## 各セクションで説明すること

| セクション | 内容 |
| --- | --- |
| 変更概要 | この Group が実現すること、変更が必要な背景、PR 全体での役割。新規導入はその旨を示す |
| 振る舞い | 変更前後の差、ユーザーや他コンポーネントから見える挙動、主要な処理フローと重要な条件・例外 |
| 実装・構造 | 実現する仕組み、主要なモジュール・コンポーネント・interface、それらの連携 |
| 設計判断 | 確認できる採用理由、制約・トレードオフ、代替案を検討した記録。理由や記録を確認できなければその旨を書く |
| 後方互換性 | API、interface、データ形式、利用者への影響。破壊的変更では、何を使うとどう壊れるか |
| セキュリティ | 認証・認可、信頼境界、機密情報、公開する操作やデータ、権限の変化 |
| データ | データ構造・永続化・移行・整合性、既存データの解釈や扱いの変化 |
| パフォーマンス | 処理回数・計算量、レイテンシ、メモリ、外部リソース利用の変化。測定値とコード上の推論を区別する |
| 信頼性 | エラー・例外・障害時の挙動、リトライ・復旧、追加される依存先や失敗条件 |
| 運用・リリース | デプロイ・設定・Feature Flag・監視・ロールバック、必要な手順や前提 |
| 検証・根拠 | 主要な挙動を裏付けるテストと実行結果、重要な説明・判断の根拠、未検証・根拠不足の事項 |

## 影響分析の状態

6 観点の各本文は次の状態と、その状態を判断した範囲・根拠で始めます。英語では対応する `Impact`、`No impact`、`Not applicable`、`Unverified` を使います。

| 状態 | 使う条件 |
| --- | --- |
| 影響あり | 具体的な変化が確認できる。変化と帰結を説明する |
| 影響なし | 関連する利用箇所や処理を調べ、その範囲で影響がないと確認できる。調べた範囲と根拠を添える |
| 該当なし | その観点の対象自体がこの変更に適用されない。適用されない理由を添える |
| 未確認 | 判断に必要な情報が足りない。不足している情報や確認範囲を示す |

一つの観点に複数の事項があれば、範囲を分けて記述します。確認できる影響があっても、全体の安全性や性能まで確認できたことにはなりません。例えば「影響あり：認証済みユーザーの読み取り API が増える。新しい呼び出し元の認可要件は未確認」のように書けます。

「差分にセキュリティ関連のコードがない」だけでは、セキュリティへの影響なしとは判断しません。呼び出し経路、入力・出力、権限や信頼境界など、その変更に関係する箇所を確認します。必要な情報が得られなければ未確認とします。関係のないシステム全体の監査へ作業を広げません。

## 事実・推論・未確認と、評価の区別

コードやコミットで確認できたことは事実として書きます。推論には「推論」と分かる表現と根拠を添え、分からないことは「未確認」「判断理由は確認できない」と示します。実装からもっともらしい設計動機や代替案の検討履歴を作らないでください。実装の構造が持つ効果を説明できても、それを作者が採用した理由だとは断定しません。

説明に重要なコードは path と識別子、必要なら行番号やコミット SHA で特定します。記録された判断には、そのコミット・設計文書などの確認可能な根拠を示します。コードの細部をすべて引用する必要はありません。複数 Group にまたがる帰結は、相手の Group 名または ID と関係を示します。

テストが存在すること、テストが実際に検査している条件、実行して成功したことを分けます。実行結果を記す場合は対象とコマンドを示し、未実行のものを成功と書きません。coverage 検証の成功も、アプリケーションの正しさを確認したことにはなりません。

例えば「新しい呼び出し経路は認可チェックを経由しない」は具体的な影響です。「重大な脆弱性なので修正必須」は評価です。影響が大きそうな事実も、その事実と帰結を説明し、品質評価・採否判断へ置き換えません。

## 完成例

以下は、`src/repository.go` に ID 検索メソッドを追加し、コミット本文で更新前の照合に使うと説明されている、という仮想の変更例です。記載する挙動が実際の対象コードで確認できる場合にだけ使い、対象の実装・根拠に合わせて書き直します。

```markdown
### 1. 説明

#### 変更概要

保存済みレコードを ID で取得する手段を追加する。コミット本文は更新前の照合を目的としており、この Group はその前提となる取得処理を提供する。

#### 振る舞い

変更前の `Repository` interface には ID 検索がない。新規メソッド `FindByID` は、指定した ID のレコードを返す。呼び出し元の更新処理はこの Group に含まれず、取得した値を使う更新可否の判定まで導入したわけではない。

#### 実装・構造

既存の `Repository` interface と実装に `FindByID` を追加する。実装は ID を条件に SELECT を一回発行する。定義と取得処理は `src/repository.go` にある。

#### 設計判断

既存 interface に取得を加える構成は確認できるが、その採用理由や代替案を比較した記録は確認できない。

### 2. 影響分析

#### 後方互換性

影響あり：interface の実装側に新しいメソッドが必要になる。この変更に含まれる実装は追随している。リポジトリ外に別の実装があるかは未確認。

#### セキュリティ

未確認：ID からレコードを取得する入口が増えるが、呼び出し元の認可条件や返すデータの公開範囲はこの変更だけでは確認できない。

#### データ

影響なし：この Group の SQL は読み取りだけで、テーブル定義や保存形式を変更しない。取得対象の既存データを書き換える処理はない。

#### パフォーマンス

影響あり：メソッドを呼ぶたびに SELECT が一回発生する。呼び出し頻度と実測時間は未確認。

#### 信頼性

未確認：データベースへの問い合わせが追加されるが、対象がない場合と問い合わせ失敗時の呼び出し元の扱いは未確認。

#### 運用・リリース

未確認：変更範囲に設定や移行スクリプトの追加はないが、外部の interface 実装の有無が不明なため、リリース時の追随手順は確認できない。

### 3. 検証・根拠

#### 検証・根拠

interface と実装の追加は `src/repository.go` の `FindByID`、利用目的は変更コミットの本文に基づく。テストは未実行。更新を行う呼び出し元の動作、認可条件、性能はこの Group では未検証。
```
